Tema 5. Indirect Communication

Sistemas Actuales de Computación

Communication Models

Direct communication (topic 3): the sender names the receiver, and both have to be alive.

  • One-to-One: Sockets, RPC, Web Services

  • One-to-Many:

    • Broadcast: 1 to all
    • Multicast: 1 to many (Group Communication)

Indirect communication puts an intermediary between them: a group, a broker, or a queue.

A real-example

In what situation within our “service-human” world can we observe group communication?

Space and time uncoupling

  • Space uncoupling: the sender does not know the identity of the receiver(s). Participants can be replaced, updated, replicated, or migrated.
  • Time uncoupling: sender(s) and receiver(s) can have independent lifetimes. They do not have to be running at the same time.
Time-coupled Time-uncoupled
Space coupling message passing, remote invocation Email
Space uncoupling IP multicast, process groups durable pub/sub, message queues

Email is space-coupled: the sender writes to a known address. It is time-uncoupled: the recipient can be offline.

A process group is space-uncoupled, but time-coupled if there is no retention. A member that joins later does not receive messages sent before it joined. Durable pub/sub and queues keep the message, so the receiver can show up afterwards.

Groups

A group treats a collection of processes as one abstraction. The sender addresses the group, not each member.

Groups are dynamic:

  • Groups are created and destroyed
  • Processes may join and leave
  • A process may belong to zero or more groups

Groups in DS

Group communication is used for:

  • Reliable dissemination to a large number of clients
  • Collaborative applications
  • Fault-tolerance strategies, such as replicated servers
  • System monitoring and management

Design issues: who talks, and who belongs

  • Closed vs. open

    • Closed: only members can send to the group
    • Open: any process can send, even if it is not a member

  • Peer vs. hierarchical

    • Peer: each member communicates with the whole group
    • Hierarchical: communication goes through a coordinator. There may be a root coordinator

  • Membership, creation, and deletion

    • Centralized: one manager admits joins and leaves
    • Distributed: the members agree on membership themselves

Message order

The network does not preserve a single order. The group has to choose one.

  • FIFO. Messages from the same sender are delivered in send order.
  • Causal. If \(m_1 \rightarrow m_2\), no member delivers \(m_2\) before \(m_1\). Vector clocks (Unit 4) detect that precedence.
  • Total. Every member delivers the same sequence.

\(P_1\) sends \(m_1\), then \(m_2\). \(P_2\) receives \(m_1\) and then sends \(m_3\).

  • FIFO puts \(m_1\) before \(m_2\), and says nothing about \(m_3\) against \(m_2\).
  • Causal also puts \(m_1\) before \(m_3\), because \(m_3\) was sent after receiving \(m_1\).
  • Total picks one sequence for every replica, for example \(m_1, m_3, m_2\).

The order log of the order service needs total order. A causal chat does not.

Views and virtual synchrony

A view is the membership that is current (Birman 1986)

Joining and leaving have to be synchronous with message delivery. Otherwise two replicas can apply a different set of updates during the same failure.

Virtual synchrony:

  • Members that survive a view deliver the same messages of that view
  • A view change is an event in that sequence, not a silent edit of a list
  • The new view is installed only after the messages of the previous view have been delivered to the survivors

Crash of a replica in the order service: the survivors agree on a view without it, and they agree on which updates belong to the old view.

Failures of a multicast

These are not a general catalogue. Each one breaks a different part of the group.

  • Crash. The process stops communicating. The group must install a new view without it.
  • Omission. A send or a receive is lost, usually in the network. Retransmission can repair it. Membership does not have to change.
  • Byzantine. A member sends conflicting messages to different peers. Retransmission and views assume crash or omission, not this.
  • Partition. The network splits the group into subgroups that cannot see each other. Each side may install its own view and keep deciding. That split brain is the failure membership has to define a rule for: which side, if any, remains the group.

Delivery guarantees

Ordering says in what sequence. Delivery says how many times.

Guarantee Meaning
Unreliable the message may be lost
At most once zero or one delivery; duplicates are dropped; loss is still possible
At least once retransmit until it is accepted; duplicates are possible (ACKs messages)
Exactly once at least once, plus the receiver discards duplicates (Santo Grial)

Reliability of multicast

“Unreliable” and “At most once multicast” send it and hope every member receives it. Cheap, and wrong for the order log.

Acknowledgements:

  • Send the message to each member
  • Wait for an acknowledgement from each member
  • Retransmit to members that do not answer
  • One message out, a huge number of ACKs back: feedback implosion

Optimizing acknowledgements

Technique Idea Cost
Pipelining send several messages; ACKs return asynchronously; a timeout retransmits what is missing a timer per message
Cumulative ACKs one ACK covers every message received so far the ACK waits
Piggybacked ACKs the ACK rides inside a message going the other way needs traffic in both directions
Negative ACKs messages carry a sequence number; the receiver asks for the ones it missed the sender keeps the history; a dead receiver never complains

A negative ACK is efficient while receivers are alive. It does not discover a member that has crashed: that is a membership problem, solved with views.

Group Communication ways

  • Publish-subscribe
  • Message queues

Publish-subscribe

Producers publish messages. Consumers express an interest. A broker does the matching. Publisher and subscriber do not name each other.

  • Publisher: sends a notification
  • Subscriber: registers a filter
  • Broker: stores subscriptions and routes the notifications that match

In the order service, the warehouse subscribes to “order shipped”. It does not know which replica published the event.

Subscription models

Model What is matched Example
Channel-based a physical channel CORBA Event Service
Topic-based the subject name Google Pub/Sub
Content-based a predicate over fields “city = Palma and total > 100”
Type-based the object type in the message OrderShipped

The filter can run in three places:

  • At the publisher. Fewer messages leave. The publisher must know the subscriptions.
  • At the broker. Publishers stay simple. The broker pays for the matching.
  • At the subscriber. The broker may flood. The subscriber throws away what it does not want.

Message queues

The queue is the intermediary. The producer does not name the consumer, and the consumer does not have to be running when the message is sent. The message waits.

  • Point-to-point. Competing consumers: each message is taken by one worker. Two packing stations share the preparation queue; a parcel is packed once.
  • Publish-subscribe through the same system. Each subscriber has its own copy.

Three operational rules:

  • Persistence. The message survives a restart of the broker.
  • Retries. A consumer that fails can be given the message again. That is at-least-once delivery.
  • Poison message. A message that always fails processing. After a retry limit it leaves the main queue, usually to a dead-letter queue, so one bad message does not block the rest.

A log as intermediary

One concrete picture, in the style of Kafka:

  • A topic is the retained log of events (“order shipped”, “prepare parcel”)
  • A consumer group is a set of workers sharing that topic. Each record is delivered to one member of the group
  • An offset is a consumer’s position in the log. After a restart it continues from that position instead of the beginning

The consumer group is the group. The topic is the subscription. The retained log is the queue. One system, the three roles of this unit.

Which intermediary?

Style Receivers chosen by Persistence Typical use
RPC, message passing the sender no call a known service
Process group the membership usually no reliable, ordered broadcast among replicas
Publish-subscribe the subscriber, via a filter depends on the broker event notification
Message queue the queue; consumers compete yes decoupled work and load sharing

Back to the order service:

  • Replicas of the order log → group, total order, exactly-once apply
  • “Order shipped” → pub/sub, topic or content filter
  • Packing tasks → queue, competing consumers, at least once plus a check that the parcel was not already packed
