Sockets

  • Dominant API for Transport layer connectivity.

  • Created at UC Berkeley for 4.2BSD Unix (1983)

  • Design goals:

    • Communication between processes should not depend on whether they are on the same machine
    • Communication should be efficient
    • Interface should be compatible with files (stdio,stdout)
    • Support different protocols and naming conventions.

Sockets

A socket is an abstract object from which messages are sent and received. Like a file descriptor.

Sockets. Connection-oriented (TCP) socket operations

Client

  • Create socket: socket
  • Name the socket (local address, port): bind
  • Connect to the other side: connect
  • read / write byte streams: read/write
  • Close the socket: close

Server

  • Create socket: socket
  • Name the socket (local address, port): bind
  • Set the socket for listening: listen
  • Wait for and accept a connection; get a socket for the connection: accept
  • read / write byte streams: read/write
  • Close the listening socket: close
  • Close the socket: close

Sockets. Connectionless (UDP) socket operations

Client

  • Create socket: socket
  • Name the socket (local address, port): bind
  • Send a message: send to
  • Receive a message: recvfrom
  • Close the socket: close

Server

  • Create socket: socket

  • Name the socket (local address, port): bind

  • Receive a message: recvfrom

  • Send a message: send to

  • Close the socket: close

RPC Issues

More RPC Issues/Problems:

  • Interoperability: different languages, OS, Hardware

  • Firewalls: dynamic ports

  • State: load balancing, resources, network failures,…

  • No group communication - no replication

  • No asynchronous messaging:

    • Large streaming responses not possible
    • Notifications of delays not possibly
    • No subscribe-publish models

Internet and Web services

Service-Oriented Architecture: Emerged in the context of web services to allow systems developed with different technologies to communicate through a common format. Their messages use XML and are typically transported over HTTP.

Service-Oriented Architecture (SOA)

Benefits of SOA:

  • Autonomous modules, and support reuse of modules across the applications

  • Loose coupling:

    • Requires minimal knowledge
    • Migration: services can be located and recolated on any servers
    • Scalability: new services can be added/removed on demmand…and on different server.. or load balanced
    • Updates: individual services can be replace without interruption

Simple Object Access Protocol (SOAP)

SOAP (Simple Object Access Protocol) is a protocol for exchanging structured messages between applications. A SOAP message is written in XML and is commonly sent over HTTP. It has an Envelope containing an optional Header and a Body. If processing fails, the Body can contain a Fault describing the error.

WSDL (Web Services Description Language). The WSDL describes the available operations, the data they accept and return, and where to send requests. This lets a client call a service without knowing how the server is implemented.

Example: OTA Standard - XML messages exchanged by the standard interface are based on standard Open Travel Alliance (OTA) 2003.

  • http://www.opentravel.org/
  • https://ota-doc.weekendesk.com/#introduction

anyAI: “generate a basic WSDL example”

<?xml version="1.0" encoding="UTF-8"?>
<definitions
    xmlns="http://schemas.xmlsoap.org/wsdl/"
    xmlns:soap="http://schemas.xmlsoap.org/wsdl/soap/"
    xmlns:tns="http://example.org/calculator"
    xmlns:xsd="http://www.w3.org/2001/XMLSchema"
    targetNamespace="http://example.org/calculator"
    name="CalculatorService">

  <types>
    <xsd:schema targetNamespace="http://example.org/calculator">
      <xsd:element name="AddRequest">
        <xsd:complexType>
          <xsd:sequence>
            <xsd:element name="a" type="xsd:int"/>
            <xsd:element name="b" type="xsd:int"/>
          </xsd:sequence>
        </xsd:complexType>
      </xsd:element>

      <xsd:element name="AddResponse">
        <xsd:complexType>
          <xsd:sequence>
            <xsd:element name="result" type="xsd:int"/>
          </xsd:sequence>
        </xsd:complexType>
      </xsd:element>
    </xsd:schema>
  </types>

  <message name="AddInput">
    <part name="parameters" element="tns:AddRequest"/>
  </message>
  <message name="AddOutput">
    <part name="parameters" element="tns:AddResponse"/>
  </message>

  <portType name="CalculatorPortType">
    <operation name="Add">
      <input message="tns:AddInput"/>
      <output message="tns:AddOutput"/>
    </operation>
  </portType>

  <binding name="CalculatorBinding" type="tns:CalculatorPortType">
    <soap:binding style="document"
                  transport="http://schemas.xmlsoap.org/soap/http"/>
    <operation name="Add">
      <soap:operation soapAction="http://example.org/calculator/Add"/>
      <input><soap:body use="literal"/></input>
      <output><soap:body use="literal"/></output>
    </operation>
  </binding>

  <service name="CalculatorService">
    <port name="CalculatorPort" binding="tns:CalculatorBinding">
      <soap:address location="https://example.org/calculator"/>
    </port>
  </service>
</definitions>

gRPC (2015) “de Google RPC”

A gRPC service is defined in a .proto file using Protocol Buffers. This file specifies the available methods and the structure of their request and response messages. Client and server code can then be generated from the same definition. gRPC commonly uses HTTP/2 to transport messages.

calculator.proto example:

syntax = "proto3";

service Calculator {
  rpc Add(AddRequest) returns (AddResponse);
}

message AddRequest {
  int32 a = 1;
  int32 b = 2;
}

message AddResponse {
  int32 result = 1;
}
