Coordination

Techniques to coordinate actions and agree on shared value in Distributed Systems:

  • Atomic commitment: participants need to agree on a value, but they have specific constraints on whether they can accept any particular value. i.e. ¿Quedamos?
  • Consensus: participants need to agree on a value, but they are willing and capable to accept any value. Ie. ¿Cuándo quedamos?
  • Shared resource (critical section) may require exclusive access: Distributed mutual exclusion

Examples:

  • Update fields in database tables
  • Modify a file
  • Modify file contents that are replicated on multiple servers

Distributed Mutual Exclusion:

  • Easy, if the entire request is atomic
  • Needs to be coordinated: if the requests comprises multiple messages or spans multiple systems.

Agreement is hard

In the asynchronous system model, it is impossible to guarantee agreement in finite time under all failure scenarios.

The consensus problem can be approached in practice: there exist protocols to solve consensus under vast majority of plausible failure scenarios.

That’s not the case for atomic commitment: if each participant has their own constraints, then you can’t tolerate any one participant’s failure.

In that sense, atomic commitment is even harder than consensus.

Consensus

Three requirements for a solution:

  • consistency: once a value is chosen, the chosen value of all working processes is the same.
  • termination: eventually they agree on a value (a.k.a., a value is “chosen”).
  • validity: the chosen value was proposed by one of the nodes.

But there are failures:

  • Crash failure: a node does not reply
  • Omission failures: some lost messages (solution: Paxos / Raft)
  • Byzantine failures: arbitrary behaviour of a node (solution: Practical Byzantine Fault Tolerance (PBFT) (Castro and Liskov 1999) / Tendermint)

(a Case) requirements for a solution:

  • Consistency: both armies decide to attack at the same time.
  • Termination: each army decides to attack after a finite number of messages.
  • Validity: the time to attack was proposed by one of the armies.

Remembering the Byzantine problem

Several generals must agree on one plan: attack or retreat (Lamport et al. 1982). They only communicate by messenger. Some generals are traitors.

A traitor can send attack to one loyal general and retreat to another. The loyal ones still have to:

  • Consistency: all of them adopt the same plan
  • Validity: if the commander is loyal, that plan is the commander’s order

With oral messages, three generals cannot tolerate one traitor. Each loyal lieutenant hears a different order and cannot tell who lied. The bound is the one PBFT uses next: \(n \ge 3f + 1\) loyal and traitor generals to cope with \(f\) traitors.

A crash only goes silent. A Byzantine node can lie, and can lie differently to each peer.

Lamport’s solution: \(n \ge 3f + 1\)

Oral messages: delivery is reliable, the receiver knows the sender, and silence is detectable (Lamport et al. 1982). A traitor may still say anything.

For one traitor, four generals suffice. The commander sends an order. Each lieutenant then tells the others what he heard, and every loyal lieutenant decides by majority.

  • The commander is loyal and one lieutenant lies. A loyal lieutenant collects the true order twice and the lie once. Majority recovers the order.
  • The commander is the traitor. The lieutenants are loyal, so they all assemble the same vector of received orders and the majority is the same plan. A tie defaults to retreat.

For \(f\) traitors that exchange is repeated \(f\) times. Reporting what you were told is a smaller Byzantine agreement, with one traitor fewer. Each level needs three voices for every traitor, so \(n \ge 3f + 1\) throughout.

Practical Byzantine Fault Tolerance (PBFT)

Consensus when replicas may lie, not only crash (Castro and Liskov 1999). Paxos and Raft are no longer safe under that fault.

  • Tolerates \(f\) Byzantine replicas if \(n = 3f + 1\)
  • A decision needs a quorum of \(2f + 1\). Any two quorums share at least one correct replica, so they cannot commit two different values
  • A primary assigns the order. The other replicas audit it

One client request, three rounds:

  1. Pre-prepare. The primary proposes a sequence number
  2. Prepare. \(2f\) matching prepares: the replica agrees on that order
  3. Commit. \(2f + 1\) commits: enough correct replicas will execute it

The client accepts the answer when \(f + 1\) replies match. If the primary is silent or contradicts itself, a view change elects another and keeps requests that were already prepared. Termination still needs partial synchrony: eventually, messages arrive before the timeout.

Practical Byzantine Fault Tolerance (PBFT)

Tendermint

The same Byzantine quorum, used to agree on the next block of a chain (Buchman et al. 2018). Validators may have weighted votes, and the set of validators is known. A committed block is final: a longer chain does not replace it.

Each height proceeds in rounds, and each round has a proposer.

  1. Propose. The proposer broadcasts a block. If it is locked on an earlier block, it must propose that one
  2. Prevote. Validators vote for that block, or for nil
  3. Precommit. A validator that sees \(2f + 1\) prevotes for the same block precommits it and locks on it

\(2f + 1\) precommits commit the block, and the height advances. Otherwise the round times out and the next proposer tries. The lock is the safety argument across rounds: after precommitting, a correct validator does not vote for a conflicting block.

Where PBFT keeps one primary to order client operations, Tendermint rotates the proposer, and the value agreed on is a block in a log.

Tendermint: one round

Four validators, so \(f = 1\) and a quorum is \(2f + 1 = 3\). \(V_1\) proposes block \(B\). The arrows into \(V_1\) are the votes it counts; \(V_2\), \(V_3\) and \(V_4\) count the same broadcast.

  • Propose. One broadcast of \(B\). A locked proposer would have to send the locked block instead
  • Prevote. Three votes for \(B\) let a validator precommit and lock \(B\)
  • Precommit. Three precommits commit \(B\). The height advances, and the lock is released

Tendermint pseudo-algorithm

\(n = 3f + 1\) validators. A decision needs \(2f + 1\) votes. nil is a vote for “no block”.

lockedValue := nil          # block this validator must keep
round := 0

while the height is not committed:
    proposer := proposer for this height and round

    PROPOSE
        if I am the proposer:
            propose lockedValue, or a new valid block if not locked
        else:
            wait for the proposal, or for the timeout

    PREVOTE
        if the proposal is valid and does not conflict with lockedValue:
            prevote the proposal
        else:
            prevote nil
        wait for 2f + 1 prevotes, or for the timeout

    PRECOMMIT
        if 2f + 1 prevotes name the same block v:
            lockedValue := v
            precommit v
        else:
            precommit nil
        wait for 2f + 1 precommits, or for the timeout

        if 2f + 1 precommits name the same block v:
            commit v and start the next height
            lockedValue := nil
            round := 0
        else:
            round := round + 1

A correct validator that has precommitted \(v\) does not prevote a different block in a later round. That lock is why two rounds cannot commit two blocks at the same height.

Distributed Mutual Exclusion

Create an algorithm to allow a process to request and obtain exclusive access to a resource that is available on the network

Required properties:

  • Safety: at any instant, only one process may hold the resource
  • Liveness: every request is eventually granted

Also desired:

  • Fairness: each process gets a fair chance to hold the resource: bounded waiting and in-order service

Liveness and fairness hold only under the assumptions on the next slide. A holder that never releases the resource, or a process that stops answering, blocks the rest.

Distributed Mutual Exclusion: Assumptions

These are the hypotheses of the basic algorithms (Lamport, Ricart-Agrawala), not properties of a real network.

  • Resource name. Processes agree on how a resource is identified and pass that name in the request: request(Resource).
  • Process identity. Every process has a unique id. It breaks ties between requests that carry the same logical time.
  • Known group. The set of processes that share the resource is finite and known. Each request is sent to all of them.
  • Reliable channels. Messages between a pair are eventually delivered, in send order. Retransmission builds that channel; it is not part of the exclusion algorithm.
  • No failures. Processes do not crash and do not stop replying. If the holder dies, or a reply never comes, the others wait forever. Leases, failure detection, or a new coordinator are a different algorithm, and safety is no longer free.
  • Release. A process that holds the resource eventually releases it.
  • Asynchrony. There is no bound on message delay or on process speed. A timeout cannot tell a crash from a slow process, so these algorithms do not use one. They rely on every process eventually answering. Granting the resource because a timeout expired can give it to two processes and break safety.

Performance metrics

The performance is generally measured by the following four metrics:

  • Message complexity: The number of messages required per Critical Section (CS) execution by a system.
  • Synchronization delay: After a system leaves the CS, it is the time required and before the next system enters the CS
  • Response time: The time interval a request waits for its CS execution to be over after its request messages have been sent out
  • System throughput. The rate at which the system executes requests for the CS

\[ X_{System} = \frac{1}{Delay+CS_{Duration}} \]

Types of mutual exclusion algorithms

  • Centralized. A process can access a resource because a central coordinator allowed it to do so.
  • Token-based. A process can access a resource if it is holding a token permitting it to do so.
  • Contention-based / Quorum-based. A process can access a resource via distributed agreement.

Centralized algorithms

  • Mimic single processor system

  • One process elected as coordinator (Leader election problem):

    1. Request resource
    2. Wait for response
    3. Receive grant
    4. Access resource
    5. Release resource

If another process claimed resource:

  • Coordinator does not replay until release- Maintain queue: service requests in FIFO order

Centralized algorithms

Benefits:

  • Fair: all requests processed in order
  • Easy to implement, understand, verify
  • Processes do not need to know group members
  • Efficiency: 2 messages to enter, 1 message to exit

Problems:

  • Process cannot distinguish being blocked from a dead coordinator
  • single point of failure
  • Centralized server can be a bottleneck

Token Ring algorithms

Assume known group of processes

  • Some ordering can be imposed on group (unique process IDs)
  • Construct logical ring in software
  • Process communicates with its neighbour

Token Ring algorithms

Safety:

  • Only one process at a time has token. Mutual exclusion guaranteed.

Liveness:

  • Order well-defined. Starvation cannot occur. Lack of FCFS ordering may be undesirable sometimes.

Delay:

  • Request = 0..N-1 messages
  • Release = 1 message

Problems:

  • Constant activity
  • Token loss (e.g. process died)
  • Process loss (neighbour disappears)
  • Total Casual-ordered requests to entry to the CS

Contention-based

A process can access a resource via distributed agreement

  • Lamport’s mutual exclusion (Lamport 1978)
  • Ricart & Agrawala algorithm (Ricart and Agrawala 1981)

Lamport’s mutual exclusion

Distributed algorithm: logical clocks and a request queue at every process (Lamport 1978).

  • Each message is sent to every other process, reliably, and FIFO from each sender
  • The clock advances on send and on receive, so a reply is stamped later than the request it acknowledges
  • The decision order is the pair \((T_i, i)\). The timestamp alone is not unique; the process id breaks ties. Every process compares those pairs the same way
  • Each process keeps a queue of pending requests, sorted by \((T_i, i)\)

The queues are not identical at every instant: a request still in transit is missing at some processes. The entry rule is what makes that safe.

Lamport’s mutual exclusion

First step: request the resource

  • \(P_i\) sends Request \((R, i, T_i)\) to every other process, and puts that same request on its own queue
  • When \(P_j\) receives it, \(P_j\) inserts the request in its queue and returns a timestamped Reply \((T_j)\), with \(T_j > T_i\)

Lamport’s mutual exclusion

Second step: use the resource

\(P_i\) enters only when both conditions hold:

  • A Reply \((T_j)\) has arrived from every other \(P_j\) with \(T_j > T_i\). Because the channel is FIFO, no earlier request from \(P_j\) is still on its way
  • \(P_i\)’s own request is the earliest pair \((T_i, i)\) in its queue

Lamport’s mutual exclusion

Third step: release the resource

  • \(P_i\) deletes its request from its own queue and sends Release \((i, T_i)\) to every other process
  • Each recipient deletes \(P_i\)’s request from its queue
  • A waiting process may then enter, but only if its request is now the earliest and it already has a later reply from everyone. Release removes the process ahead; it does not by itself grant the critical section

Lamport’s mutual exclusion: example

\(P_1\) and \(P_2\) both request at Lamport time 1. The pairs decide: \((1,1) < (1,2)\), so \(P_1\) enters first. \(P_3\) only replies.

  • \(P_1\) enters at time 4: both replies are later than 1, and \((1,1)\) is at the head of the queue
  • \(P_2\) already has its replies, but \((1,2)\) sits behind \((1,1)\). It enters at time 5, when \(P_1\)’s release arrives

Lamport’s mutual exclusion

Safety: the pair \((T_i, i)\) is one total order at every process. \(P_i\) enters only after a later message from every peer, so any request that should come first is already in the queue, and \(P_i\) is at the head.

Liveness: if nobody fails and every holder releases, the earliest request eventually has its replies and reaches the head. That request enters.

Fairness: requests are served in timestamp order, not in the order the network delivered them.

Delay: each execution sends \((N-1)\) requests, \((N-1)\) replies and \((N-1)\) releases. Total: \(3(N-1)\) messages.

Problems:

  • Any silent process blocks entry: the algorithm waits for every peer
  • Every request and every release is sent to the whole group

Ricart & Agrawala algorithm

Same clocks and the same pair \((T_i, i)\) as Lamport (Ricart and Agrawala 1981). The release multicast disappears: permission is a reply, and a reply can be postponed.

To enter the critical section, \(P_i\):

  1. Sends Request \((R, i, T_i)\) to every other process
  2. Waits until \((N-1)\) replies have arrived
  3. Enters

A peer does not always reply at once. It replies immediately only if it does not need the resource first.

Ricart & Agrawala algorithm

Each process is in one state: RELEASED, WANTED, or HELD. The pair order is \((T, p) < (T', q)\) when \(T < T'\), or when the timestamps are equal and \(p < q\).

state := RELEASED

enter():
    state := WANTED
    T := Lamport time of this request
    send Request(R, i, T) to every other process
    wait for (N - 1) replies
    state := HELD

on Request(Ti, pi) at pj, i ≠ j:
    if state = HELD
       or (state = WANTED and (T, pj) < (Ti, pi)):
        queue pi          # reply later
    else:
        reply to pi       # at once

exit():
    state := RELEASED
    reply to every queued request

If \(P_j\) is in the critical section, or it is waiting with an earlier pair, it withholds the reply. Otherwise it replies immediately, including when it is waiting with a later pair.

Ricart & Agrawala algorithm: example

The same two requests, \((1,1) < (1,2)\). There is no release. The missing arrow is the point: \(P_1\) does not answer \(P_2\) when the request arrives.

  • \(P_2\) is waiting, but with a later pair, so the reply to \(P_1\) leaves at once
  • \(P_3\) is idle, so both of its replies leave at once
  • \(P_1\) has the earlier pair, queues \(P_2\), and enters as soon as those two replies have arrived
  • On exit, \(P_1\) sends the reply it had withheld. That dashed arrow, not a release, is what lets \(P_2\) in

Ricart & Agrawala algorithm

Safety: two competing processes do not reply to each other. The later pair replies; the earlier pair defers its reply until it leaves. Both cannot be in the critical section. The pair \((T_i, i)\) is unique, so one of the two is earlier.

Liveness: the pending request with the smallest pair receives a reply from every peer. A process that is only waiting, and has a larger pair, replies at once. It does not defer. If nobody fails and every holder leaves, that smallest request collects \((N-1)\) replies.

Fairness: among overlapping requests, the smaller pair enters first.

Delay: \((N-1)\) requests and \((N-1)\) replies, so \(2(N-1)\) messages per entry. There is no release multicast. On exit the process sends the replies it had postponed, from \(0\) to \((N-1)\). Those messages are the replies the waiting processes already count in their own \(2(N-1)\).

Problems:

  • Any silent process blocks entry: \((N-1)\) replies are required
  • Every request is still sent to the whole group

Comparison

Both use the pair \((T_i, i)\). They differ in who replies, and in what a process needs before it enters.

Lamport Ricart & Agrawala
Reply Always, at once. No hold-back At once, unless the receiver is in the critical section or waiting with an earlier pair
Enter when Own request is the earliest in the queue, and a later reply has arrived from every peer \((N-1)\) replies have arrived
Release Multicast Release to the group; each peer deletes that request No release multicast. Reply only to the queued requests
Messages per entry \(3(N-1)\): request, reply, release \(2(N-1)\): request, reply

Maekawa’s algorithm

Maekawa’s algorithm is the first quorum-based mutual exclusion algorithm (Maekawa 1985). A process does not ask the whole group. It asks the members of its voting set, and it enters when every one of them has replied.

It differs from Lamport and from Ricart & Agrawala in two ways:

  • The request goes to a subset, not to all \(N-1\) peers
  • A process grants its vote to one requester at a time. It grants the next vote only after the previous holder has released it

Voting sets

Each process \(p_i\) has a voting set \(V_i \subseteq \{p_1, \ldots, p_N\}\):

  • \(p_i \in V_i\)
  • \(V_i \cap V_j \neq \emptyset\): any two voting sets share at least one process
  • \(|V_i| = K\): every voting set has the same size
  • each process \(p_j\) belongs to \(M\) voting sets

A fair construction takes \(K \approx \sqrt{N}\) and \(M = K\). The shared member is what makes the exclusion work: two candidates always have one voter in common, and that voter has only one vote.

Building a voting set

When \(N\) is a square, place the \(N\) processes in a \(\sqrt{N} \times \sqrt{N}\) grid. The voting set of \(p_i\) is its row together with its column.

Then \(K = M = 2\sqrt{N} - 1\). Any two sets intersect: they share a row, they share a column, or the row of one crosses the column of the other.

Maekawa’s bound \(K \approx \sqrt{N}\) is a little smaller. It needs a projective plane, which exists only for some \(N\). For \(N = 7\) the sets have size \(3\).

Voting sets: example

\(N = 4 = 2 \times 2\), so \(K = 2\sqrt{4} - 1 = 3\).

column 1 column 2
row 1 \(P_1\) \(P_2\)
row 2 \(P_3\) \(P_4\)
  • \(V_1 = \{P_1, P_2, P_3\}\)
  • \(V_2 = \{P_2, P_1, P_4\}\)
  • \(V_3 = \{P_3, P_1, P_4\}\)
  • \(V_4 = \{P_4, P_2, P_3\}\)

\(V_1 \cap V_2 = \{P_1, P_2\}\), and every other pair also shares a process. Each process appears in exactly \(M = 3\) sets. To enter, \(P_1\) needs replies from \(P_1\), \(P_2\) and \(P_3\) only.

Maekawa’s algorithm

state := RELEASED
voted := FALSE

enter():
    state := WANTED
    send Request to every process in Vi
    wait until K replies have arrived
    state := HELD

on Request from pi at pj:
    if state = HELD or voted = TRUE:
        queue pi
    else:
        reply to pi
        voted := TRUE

exit():
    state := RELEASED
    send Release to every process in Vi

on Release at pj:
    if the queue is not empty:
        pk := head of the queue
        reply to pk
        voted := TRUE
    else:
        voted := FALSE

The vote stays with one requester. A queued request gets that vote only when the release arrives.

Maekawa’s algorithm

Safety: \(V_i \cap V_j\) is never empty, and the process in that intersection grants one vote. Two candidates cannot both collect \(K\) replies.

Liveness: this version can deadlock. \(P_1\) may hold \(P_2\)’s vote while \(P_2\) holds \(P_1\)’s vote, and each waits for the missing reply. Maekawa breaks the wait with the pair \((T_i, i)\): the later request returns the vote.

Delay: one entry sends \(K\) requests, \(K\) replies and \(K\) releases, so \(3K\) messages. With the grid, \(K = 2\sqrt{N}-1\). With a projective plane, \(K \approx \sqrt{N}\), and the cost is about \(3\sqrt{N}\) instead of \(3(N-1)\).

Problems:

  • Deadlock, unless a later request yields its vote
  • A silent member of \(V_i\) still blocks entry, but only the members of \(V_i\) are asked
